事情是这样的。

前两天刷到 Claude Code 的新功能，叫 dynamic workflows。我一开始没当回事，想着不就是 workflow 吗，这词儿都听烂了。Workflow engine 满大街都是，从 Airflow 到 Temporal，从 LangChain 到 Dify，哪个不是在搞 workflow。

但看完官方博客，我有点愣住。

Claude Code 的做法跟我想的完全不一样。它不是让你提前画好一张流程图然后往里塞节点，而是让 Claude 自己根据当前任务，临时写一份 JavaScript orchestration script，然后交给一个独立的 runtime 在后台跑。中间结果存在脚本变量里，不再一股脑堆进主会话上下文。主会话最终拿到的，是经过合成和验证之后的结果。

我当时就反应过来了。

我一直以为我理解 dynamic workflow，结果我只理解了 workflow，压根没理解 dynamic。

这俩字的差别，大到离谱。

说到 workflow，这东西确实能解决不少问题。你把一个复杂任务拆成几个节点，前一个节点产出结果，后一个节点继续处理。比如做一个热点新闻短视频系统，流程很容易想成这样，获取热点新闻，分析新闻，生成摘要，生成脚本，生成视频。逻辑顺，链路清晰，每一步都有职责，每一步都能留下输出。开发者看日志的时候，知道系统卡在了新闻抓取、摘要生成、脚本生成，还是视频工具。哪个环节出问题了，回去查那一段就行，不用在几十轮对话里翻模型从哪开始跑偏。

Workflow 能减少步骤遗漏，让依赖关系更清楚，把状态从一大段聊天记录里拆出来，让前一个节点的输出变成后一个节点的输入。错误也更容易追溯。

但我当时只理解了这些，没理解 dynamic 到底指什么。

Claude Code 的做法让我重新想了一件事。在垂直业务里，开发者到底该写一条流程，还是该写一套能生成流程的规则。

我举个例子你就明白了。

热点新闻短视频系统，听起来特别适合 workflow。系统先抓热点，再分析新闻，再生成脚本，再生成画面，再配音，再合成视频。开发者可以画出一张很清楚的流程图，自我感觉良好。

但真实输入不会按这张图排队。

有些热点只有文字，没有视频素材。系统要先写脚本、分镜、画面提示词和配音稿，再使用生成工具。有些热点已经有现场视频，系统继续生成画面就很别扭，它该走素材筛选、剪辑、字幕、封面和节奏优化。有些热点来自多个来源，信息互相冲突，系统如果直接写脚本，就会把不确定的信息包装成确定叙事，流程要先插入事实核验。有些新闻涉及事故、金融、公共安全或人物争议，系统不能只追求速度，它需要风险审核、敏感表述检查，必要时还要让人确认。

开发者如果提前写死一条流程，系统只能处理那条流程适配的输入。输入一变，流程就开始变形。你会在每个节点里加 if-else，给摘要节点塞风险判断，给视频节点塞事实核验，给发布节点塞人工审核。流程图看起来还在，真实逻辑已经散落在各个节点里。

说实话，我自己也踩过这个坑。之前做过一个内容生成系统，一开始画了一张特别漂亮的流程图，信誓旦旦觉得这回稳了。结果上线两周，流程图上的每个节点都被迫长出了各种分支判断，到后来我自己都看不明白这张图到底在表达什么。代码review的时候，同事指着流程图问我，这上面画的是 A 到 B 到 C，代码里怎么每个节点都在调用另外三个服务。我当时也挺尴尬的，只能说业务太复杂了。

现在想来，这种尴尬完全是自己造成的。我以为画了一张图就能管住真实世界，但真实世界从来不会按图索骥。

workflow 会给人一种假稳定。表面上每一步都固定，实际每个节点都在处理不属于自己的问题。

说到这，可能有人会想，那干脆别写流程了，直接把目标丢给 Agent，让它自己决定先搜什么、看什么、写什么、用什么工具。

请把今天最值得传播的热点新闻做成一条短视频。

Agent 确实可以自己决定。它可能给出不错的结果，也可能绕过关键步骤。它觉得某个来源可信，就直接写进脚本。它觉得视频需要冲突感，就强化一个未经确认的细节。它觉得节奏太平，就加一句吸引眼球但不够准确的文案。

在开放式创作里，这种自由有时能带来惊喜。但在垂直业务里，惊喜经常伴随风险。

短视频生产还要处理来源、事实、版权、风控、素材状态、平台规则和发布时间。开发者不能只看最终视频好不好看，还要知道系统怎么走到这个结果。

业务 Agent 如果没有可观察的流程，出错时很难修。你不知道它在哪里把来源 A 和来源 B 混在了一起，也不知道它为什么跳过审核。下一次它可能换一条路，犯一个新错误。

你修 bug 的时候会发现，连复现问题都很难。因为每次让 Agent 重做，它可能走的是完全不同的路径。

所以我现在更愿意把自由放在流程生成层。模型可以决定这次任务该走哪条流程，但执行过程要落在可观察的结构里。

这才是 dynamic 的真正含义。

Claude Code 给了一个清楚的工程表达。模型先为任务生成 workflow script，runtime 再执行它。

把这个思路放到热点新闻短视频系统里，开发者不用先问完整流程应该长什么样。系统拿到输入之后，先判断几个状态。素材状态，只有文字，有视频素材，有图片素材，来源不足。事实状态，来源一致，来源冲突，无法确认。风险状态，普通娱乐，财经医疗，公共安全，人物争议。业务目标，追求速度，追求质量，追求规模化。

这些状态决定 workflow 的形状。

素材只有文字时，系统生成脚本、分镜、画面生成、配音、合成的流程。素材里有现场视频时，系统生成素材清洗、片段筛选、字幕、节奏优化、封面的流程。来源冲突时，系统先插入交叉核验、争议标注、人工确认，脚本生成要等核验结果。新闻敏感时，系统在发布前插入风险审核，审核不过，流程回到脚本修改，不继续生成视频。

你看，同一份输入，不同状态下走的链路完全不一样。

我现在理解的 dynamic，指的是系统根据任务状态生成一条合适的流程结构。流程一旦生成，就要交给 runtime 托管。每个节点做什么、由谁做、产出什么、失败后怎么办，都要留下记录。

模型负责提出结构。工程系统负责约束结构。

如果模型只生成内容，它的作用被压在局部节点里。如果模型连执行过程都完全自己掌控，业务系统会失去可控性。Dynamic workflow 站在中间，模型提出流程，runtime 管住流程。

顺着上面的再聊聊，dynamic workflow 用到垂直业务里，开发者的工作会变。

以前开发者写流程本身。先抓热点，再摘要，再生成视频。

现在开发者要写流程生成的边界。哪些状态必须先判断，哪些节点可以动态插入，哪些结果必须验证，哪些动作需要人工确认，哪些工具不能由低权限节点使用。

这比手写流程更难，也更贴近业务 Agent 的开发难点。

以热点新闻短视频为例，开发者不需要穷举所有新闻类型和素材组合。那会写出一堆脆弱分支。开发者要定义几类边界。

第一类是事实边界。来源冲突时，系统不能直接生成确定叙事。它必须进入核验节点，或者把争议写进脚本。

第二类是权限边界。负责读取公开新闻的 Agent 不该有发布权限。负责生成脚本的 Agent 不该直接使用发布接口。越靠近外部动作，权限越要收紧。

第三类是质量边界。脚本可以动态生成，但视频发布前必须过审核。审核可以是规则、另一个 Agent，也可以是人工。这个节点不能因为赶时间被模型跳过。

第四类是成本边界。很多热点不值得跑完整流程。普通娱乐新闻可以走轻量链路，高风险新闻需要更多核验，素材复杂时才值得启动多 Agent 并行。

这些边界定义清楚，动态流程才有意义。否则 dynamic 只是在给系统增加不确定性。

我见过一些团队做了 dynamic workflow，但只是让模型自己生成流程然后直接执行。出了问题之后回溯，发现模型在某个节点省略了关键步骤，而且没有任何地方记录它为什么要这么做。这时候 dynamic 反而变成了负担，因为每次执行都不一样，你连稳定复现都做不到。

说到 runtime，很多 Agent 讨论会把注意力放在 prompt 上。Prompt 重要，但 dynamic workflow 这种形态里，runtime 要接住模型生成的流程。

流程一旦由模型生成，系统必须回答几个工程问题。这个 workflow 能不能被查看，每个节点的输入输出能不能被记录，某个节点失败后系统能不能重试或回滚，中间结果会不会污染主 Agent 的上下文，多个 subagents 的输出能不能先验证再合并。

Claude Code 的 dynamic workflows 有一个重要设计。中间结果不堆在主会话里，workflow runtime 在后台执行脚本，用户可以看进度，也可以保存 workflow。任务中断后，在同一 session 里还能继续。

这个设计比看起来更重要。如果中间结果都堆在主会话里，主 Agent 很快就会被各种细节淹没，到后来连自己在解决什么问题都忘了。这在长链路任务里是致命的。

垂直业务 Agent 不能只有会调用工具的模型。它还需要执行系统。

对热点新闻短视频来说，这个执行系统至少要管住几件事。素材状态、节点输出、事实来源、审核结果、失败原因和发布权限。系统生成视频越快，风险也会越快积累。你不想让系统半夜三点自动发布一条有争议的视频，然后第二天早上醒来发现评论区已经炸了。

我现在更倾向于把 dynamic workflow 看成一种控制平面。Agent 没有消失，它被放进了更清楚的位置。它可以判断素材状态，可以生成流程，可以完成某个节点的创作，也可以审核另一个 Agent 的输出。但它不该独自吞下整个业务闭环。

讲到这，可能有朋友会想，那是不是所有任务都适合 dynamic workflow。

其实不是。

如果任务只生成一段短文案，单次模型调用就够了。如果任务只把 JSON 转成另一个格式，普通脚本更稳。如果任务只用固定素材套模板，传统 workflow 更便宜。

它适合那些长链路、状态复杂、需要交叉验证的任务。

热点新闻短视频正好有这些特征。素材可能不完整，事实可能冲突，平台规则会限制表达，业务目标还会变化。系统不能每次都走同一条路，也不能让 Agent 每次临场发挥。

Dynamic workflow 的作用不在于让系统更像人。系统面对不同输入时，先生成一条可执行的工作流，再把执行过程放到可观察的轨道上。

普通 workflow 把复杂任务拆成固定节点。Dynamic workflow 先判断当前任务需要哪些节点，再组织它们的执行关系。

如果说普通 workflow 解决的是不要漏步骤，dynamic workflow 解决的是不要在错误的输入上跑正确但不合适的步骤。

这是两种完全不同的思路，不能互相替代。

这让我想起一个挺有意思的事。

人类文明的很多进步，说到底都是在做同一件事。把原本只能依赖个人即兴发挥的东西，变成一套可以被系统接住的流程。从手工业到流水线，从口头传说到文字记录，从个人经验到操作手册。每一次变化的核心都不是消灭人的创造力，而是把创造力放到更合适的位置。

Dynamic workflow 也一样。模型不是被削弱了，而是被重新定位了。它负责生成流程结构，这是它需要发挥创造力的地方。但流程一旦生成，就要被工程系统托管、执行、验证和记录。

这个思路放在更大的历史尺度上看，其实挺一致的。人类一直在努力做一件事，把不可控的东西变得可控，但不是消灭它，而是找到合适的位置来管理它。

回到开头那个问题。我之前以为 dynamic workflow 就是 workflow 的升级版，多了点灵活性。现在我觉得，它是两种完全不同的思路。

Workflow 问的是，这件事的标准步骤是什么。Dynamic workflow 问的是，这件事在当前状态下，应该有哪些步骤。

前一个问题是静态的，后一个问题是动态的。前一个答案可以写在文档里，后一个答案必须由模型根据实时状态来生成。

而这个生成出来的答案，又必须被 runtime 接住。模型提出，系统约束。这不是谁取代谁的关系，而是一个完整的控制回路。

以前我会先问，这个业务要不要用 Agent，还是用 workflow。

现在我会多问一步。如果业务状态会变化，workflow 本身能不能被生成。生成之后，它能不能被记录、验证和暂停。

dynamic workflow 对 Agent 开发的启发就落在这里。Agent 开发不能只继续放大自由度，还要让模型学会生成一套可以被工程系统接住的流程。

至于我自己，说实话我也不确定这些想法对所有人都有用。但这是我这段时间用 Claude Code 的真实感受，也是我踩过坑之后的反思。
