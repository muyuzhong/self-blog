> **TL;DR**
>
> Claude Code 的 dynamic workflows 让 Claude 为当前任务临时生成一套 workflow script，再由 runtime 托管执行。这个功能给我的启发是：做垂直业务 Agent 时，开发者不能只手写一条固定流程，也不能把任务丢给单个 Agent 自由发挥。更有价值的方向，是让模型根据输入状态生成流程结构，再用工程系统约束它、观察它、验证它。

我一开始理解 dynamic workflow 时，还是把重点放在 workflow 上。

Workflow 像一条流水线，把复杂任务拆成多个节点。前一个节点产出结果，后一个节点接着处理。比如让系统把热点新闻做成短视频，可以写成这样：

```text
获取热点新闻 -> 分析新闻 -> 生成摘要 -> 调用视频生成 API -> 生成视频
```

这个流程能跑，也能解释。每一步都有职责，每一步都能记录输出。开发者看日志时，知道系统卡在了新闻抓取、摘要生成，还是视频 API。

Workflow 解决了单 Agent 对话里的几个老问题。

它减少步骤遗漏。它让依赖关系更清楚。它把状态从一大段聊天记录里拆出来，让前一个节点的输出变成后一个节点的输入。它也让错误更容易追溯。某个节点生成了错误摘要，后面的视频质量变差，开发者可以回头查那一段，不用在几十轮对话里找模型什么时候开始偏。

但这个理解只讲完了 workflow，没有讲完 dynamic。

Claude Code 最近的 dynamic workflows 让我换了一个角度看这件事。Claude 会根据任务临时写出一份 JavaScript orchestration script，由独立 runtime 在后台调度大量 subagents。中间结果不再堆进主会话上下文，而是留在脚本变量和 workflow 运行状态里。主会话最后拿到经过合成和验证的结果。

这件事最值得拆开看的地方，不是“可以开很多 subagents”。并行有用，但并行只是表面。Claude Code 把“流程”从对话里拿了出来，变成了一个可以生成、可以查看、可以保存、可以恢复的执行结构。

这让我开始想：如果我们做一个垂直业务 Agent，比如热点新闻短视频生成，开发者到底应该写什么？

## 固定流程很快会遇到边界

热点新闻短视频听起来适合 workflow。

系统先抓取热点，再分析新闻，再生成脚本，再生成画面，再配音，再剪成视频。这个流程很自然，也很容易画成图。

真实输入不会乖乖排队。

有些热点只有文字，没有视频素材。系统需要先写脚本、分镜、画面提示词和配音稿，再去调用生成式视频工具。

有些热点已经有现场视频。系统不该重新生成画面，它该走素材筛选、剪辑、字幕、封面和节奏优化。

有些热点来自多个来源，信息互相冲突。系统如果直接写脚本，就会把不确定的信息包装成确定叙事。这时流程要先插入事实核验。

有些新闻涉及事故、金融、公共安全或人物争议。系统不能只追求生成速度。它需要风险审核、敏感表述检查，可能还要把某个节点交给人确认。

如果开发者提前写死一条流程，系统只能处理那条流程适配的输入。输入一变，流程就开始别扭。你会在每个节点里加 if-else，给摘要节点塞风险判断，给视频节点塞事实核验，给发布节点塞人工审核。最后流程图还在，真实逻辑已经散落在各个节点里。

这时 workflow 反而会变成一种假稳定。表面上每一步都固定，实际上每个节点都在偷偷处理本不属于自己的问题。

## 完全自由的 Agent 也不适合业务系统

另一种做法，是直接把目标交给 Agent：

```text
请把今天最值得传播的热点新闻做成一条短视频。
```

Agent 可以自己决定先搜什么、看什么、写什么、调用什么工具。它可能会给出很好的结果，也可能会绕过关键步骤。它觉得某个来源可信，就直接写进脚本。它觉得视频需要冲突感，就强化一个未经确认的细节。它觉得节奏太平，就加一句吸引眼球但不够准确的文案。

在开放式创作里，这种自由有时会带来惊喜。在垂直业务里，惊喜经常伴随风险。

短视频生产不只是写作。它要处理来源、事实、版权、风控、素材状态、平台规则和发布时间。开发者不能只看最终视频好不好看，还要知道系统怎么走到这个结果。

一个业务 Agent 如果没有可观察的流程，出错时就很难修。你不知道它在哪里把来源 A 和来源 B 混在了一起，也不知道它为什么跳过审核。更麻烦的是，下一次它可能换一条路，犯一个新错误。

我现在更愿意把自由放在流程生成层，让执行过程少一点散在对话里的临场发挥。

## Dynamic 的核心是流程结构动态生成

Claude Code 的 dynamic workflows 给了我一个很清晰的表达：让模型先为任务生成一个 workflow script，再让 runtime 执行它。

把这个思路映射到热点新闻短视频系统里，开发者可以先不问“完整流程应该长什么样”。系统拿到输入之后，先判断几个状态。

比如：

```text
素材状态：只有文字 / 有视频素材 / 有图片素材 / 来源不足
事实状态：来源一致 / 来源冲突 / 无法确认
风险状态：普通娱乐 / 财经医疗 / 公共安全 / 人物争议
业务目标：追求速度 / 追求质量 / 追求规模化
```

这些状态会决定 workflow 的形状。

如果素材只有文字，系统生成一条“脚本 + 分镜 + 画面生成 + 配音 + 合成”的流程。

如果素材里有现场视频，系统生成一条“素材清洗 + 片段筛选 + 字幕 + 节奏优化 + 封面”的流程。

如果来源冲突，系统先插入“交叉核验 + 争议标注 + 人工确认”，后面的脚本生成要等核验结果。

如果新闻敏感，系统在发布前插入风险审核。审核不过，流程回到脚本修改，不继续生成视频。

我现在理解的 dynamic，指的是系统根据任务状态生成一条合适的流程结构。流程一旦生成，就要交给 runtime 托管。每个节点做什么、由谁做、产出什么、失败后怎么办，都要被记录下来。

模型负责生成结构。工程系统负责约束结构。

这个分工很重要。如果模型只生成内容，它的价值被压在局部节点里。如果模型连执行过程都完全自己掌控，业务系统又会失去可控性。Dynamic workflow 的有趣之处，正好在中间：模型提出流程，runtime 管住流程。

## 开发者设计的是边界，不是每一条路径

如果把 dynamic workflow 用到垂直业务里，开发者的工作会发生变化。

以前开发者写的是流程本身：

```text
先抓热点，再摘要，再生成视频。
```

现在开发者更应该写流程生成的边界：

```text
哪些状态必须先判断？
哪些节点可以由系统动态插入？
哪些结果必须验证？
哪些动作需要人工确认？
哪些工具不能由低权限节点调用？
```

这比手写流程更难，也更接近业务 Agent 的核心。

以热点新闻短视频为例，开发者不需要穷举所有新闻类型和所有素材组合。那会写出一堆脆弱分支。开发者要定义几类边界。

第一类边界是事实边界。来源冲突时，系统不能直接生成确定叙事。它必须进入核验节点，或者把争议写进脚本。

第二类边界是权限边界。负责读取公开新闻的 Agent，不该有发布权限。负责生成脚本的 Agent，不该直接调用发布接口。越靠近外部动作，权限越要收紧。

第三类边界是质量边界。脚本可以动态生成，但视频发布前必须过审核。审核可以是规则、另一个 Agent，也可以是人工。关键是这个节点不能被模型因为“赶时间”跳过。

第四类边界是成本边界。不是每条热点都值得跑完整流程。普通娱乐新闻可以走轻量链路；高风险新闻需要更多核验；素材复杂时才值得启动多 Agent 并行。

这些边界一旦定义清楚，动态流程才有意义。否则 dynamic 只是在给系统增加不确定性。

## Runtime 要接住 Prompt 生成的流程

很多人讨论 Agent 时，会把注意力放在 prompt 上。Prompt 重要，但 dynamic workflow 这种形态里，runtime 要接住模型生成的流程。

因为流程一旦由模型生成，系统必须回答几个工程问题。

这个 workflow 能不能被查看？  
每个节点的输入输出能不能被记录？  
某个节点失败后，系统能不能重试或回滚？  
中间结果会不会污染主 Agent 的上下文？  
多个 subagents 的输出能不能先验证，再合并？

Claude Code 的 dynamic workflows 有一个很重要的设计：中间结果不堆在主会话里，workflow runtime 在后台执行脚本，用户可以看进度，也可以保存 workflow。任务中断后，在同一 session 里还能继续。

这说明一个垂直业务 Agent 不能只有“会调用工具的模型”。它还需要一个执行系统。

对热点新闻短视频来说，这个执行系统至少要管住几件事：素材状态、节点输出、事实来源、审核结果、失败原因和发布权限。否则系统生成视频越快，风险也越快。

我现在更倾向于把 dynamic workflow 看成一种控制平面。Agent 没有消失，它被放进了更清楚的位置。它可以负责判断素材状态，可以负责生成流程，可以负责某个节点的创作，也可以负责审核另一个 Agent 的输出。但它不该独自吞下整个业务闭环。

## 它适合高价值、长链路、状态复杂的任务

Dynamic workflow 不适合所有任务。

如果任务只生成一段短文案，单次模型调用就够了。  
如果任务只把 JSON 转成另一个格式，普通脚本更稳。  
如果任务只用固定素材套模板，传统 workflow 更便宜。

它适合那些长链路、状态复杂、需要交叉验证的任务。

热点新闻短视频正好有这些特征。素材可能不完整，事实可能冲突，平台规则会限制表达，业务目标还会变化。系统不能每次都走同一条路，也不能让 Agent 每次临场发挥。

Dynamic workflow 的价值，不在于让系统“更像人”。系统面对不同输入时，先生成一条可执行的工作流，再把执行过程放到可观察的轨道上。

普通 workflow 把复杂任务拆成固定节点。Dynamic workflow 先判断当前任务需要哪些节点，再组织它们的执行关系。

如果说普通 workflow 解决的是“不要漏步骤”，dynamic workflow 解决的是“不要在错误的输入上跑正确但不合适的步骤”。

## 最后

Claude Code 的 dynamic workflows 让我重新理解了开发者在 Agent 系统里的位置。

开发者不只写 prompt，也不只画一条流程图。开发者要设计流程生成的边界。

在热点新闻短视频这种垂直业务里，这个边界包括素材状态、事实核验、权限控制、成本限制和人工确认。模型可以根据这些边界生成 workflow，但 runtime 必须托管执行过程。

我以前会先问：这个业务要不要用 Agent，还是用 workflow？

现在我会多问一步：如果业务状态会变化，workflow 本身能不能被生成？生成之后，它能不能被记录、验证和暂停？

Dynamic workflow 给我的启发落在这里：Agent 的下一步不一定是更自由，而是更会生成一套可以被工程系统接住的流程。
