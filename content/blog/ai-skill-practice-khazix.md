事情是这样的。上个月我让 Claude Code 执行一个检索行业协会的 Skill，结果它把我随口提到的一家公司年报也给翻出来了。我当时就愣住了。我在 SKILL.md 里明明写了只检索行业协会和商会，它怎么连企业文档都翻出来了。

回头检查，问题出在 description 上。我写了检索行业协会和企业信息。就这个词，企业。模型一看用户提到公司，顺手就把 Skill 给开了。

说实话，这种坑我踩过不止一次。以前我把 Skill 当成一份需要自己慢慢打磨的说明书，一个字一个字地抠。但用了一段时间之后我发现，真正有用的 Skill 从来不是一次写对的。它是从一堆失败里长出来的。而且最反直觉的一点是，你写得越认真，它反而越容易跑偏。因为你是在用自己的假设去覆盖模型的真实行为，而模型的理解方式跟你想的完全不一样。

所以这半年我换了一套做法。现在的流程大概可以分成四步。我把这套方法分享给几个朋友试了一下，反馈出奇地一致，原来还可以这么搞。第一步就是让 AI 写第一版，听起来有点离谱对吧。你想想看，我自己也是写了几十份 Skill 之后才开始这么做的。但效果确实比我自己从零开始要好得多。

方法很简单。我把任务边界说清楚，场景是什么，触发词大概有哪些，目标输出长什么样，已有的参考资料有什么，约束条件是什么，然后让 Claude 直接生成一份完整的 SKILL.md 加上目录结构。

你猜怎么着。它生成的第一版在结构上往往比我手写的更规范。

Skill 说到底就是一份给 Claude 的行为说明书。它要解决四个问题，什么时候该触发，什么时候不该触发，具体怎么做，输出要长什么样。这些东西写在 SKILL.md 的前端，后面的 references/ 放细节，scripts/ 放确定性流程，agents/ 放代理配置。这个目录结构不是我发明的，是 Claude Code 社区里慢慢沉淀下来的共识。AI 生成第一版的时候，它会自动把这些模块对齐好，反而我自己手写的时候经常把触发条件混到调用原则里，或者把字段定义塞到 SKILL.md 正文里。

说到触发条件，这里有一个我特别想强调的点。AI 生成第一版的时候，你一定要让它写出反例。

很多人写触发条件只写应该触发什么，比如帮我搜索行业协会名单。但模型其实是个过度匹配的高手。你写了协会和企业，它就以为只要出现企业两个字就该开 Skill。所以反例必须写清楚。比如，用户说我想写一段介绍行业协会的文案，这时候不该触发。用户说帮我把这些名单翻译成英文，也不该触发。

为什么反例这么重要。因为 Claude 看 Skill 的时候，description 和触发原则就是它的入口。入口一旦模糊了，后面的调用原则写得再细也没用。就像一扇门，你画的指示牌指向了错误的房间，进去之后再好的装修也救不回来。

还有一点，触发条件要用简洁的行为指令，而不是注意事项。能总结就不写 bullet point。每条规则只说一件事。默认使用用户提问语言回复。用户明确指定语言时，遵循指定语言。这样模型看了能直接照做，而不是还要在语义上绕一圈去理解你的意图。

AI 生成的第一版当然不是完美的。说白了，它做对了一件最关键的事，骨架是对的。SKILL.md 是入口，references 里的 interaction-rules 管交互逻辑，output-structure 管输出格式，entity-scope 管实体范围，schema 管字段定义，data-quality-rules 管数据质量分级。这些东西分散在不同的文件里，一个文件只负责一个主题。这个拆分的思路特别重要，因为 Skill 写到后期最大的敌人就是膨胀。所有东西塞在一个文件里，改一处牵全身，越改越不敢改。

我一般让 Claude 生成完第一版之后，会先过一遍目录结构。如果触发条件和调用原则混在一起了，就打回去重新拆。这一步花不了多少时间，但后面能省大事。然后进入第二步，做一版会失败的 Skill。这是我跟以前最大的区别。我以前总想把第一版写得尽量完善，把能想到的情况都覆盖掉。结果呢，后来发现这是不可能的。你能想到的边界情况，大概只占实际遇到的十分之一。

所以现在我的做法是，第一版故意不追求完善。让它先跑起来，故意让它在真实任务里犯错。

具体怎么做呢。找五个跟你目标场景相关的真实任务丢进去。不是那种你自己编出来的测试用例，而是真实的问题，真实的输入，真实的上下文。

然后观察它在哪里栽跟头。我通常会把失败分成四类。

第一类是触发失败。该触发的时候没触发，或者不该触发的时候误触发了。最常见的原因就是 description 写得模棱两可，模型判断错了场景匹配度。

第二类是执行失败。触发了，但输出不符合预期。比如我让它检索行业协会，它却把企业也混进来了。或者输出格式不对，字段缺失，顺序混乱。

第三类是边界失败。它把任务执行了，但是范围越界了。比如我让它只检索德国的行业协会，它顺手把奥地利的也带上了。或者我要求只使用官网信息，它从商业目录里抓了一条凑数。

第四类是材料失败。任务设计本身没问题，但参考资料不够，模型不知道该查什么。比如我让它按特定格式整理数据，但参考资料里没有提供格式模板。

这四类失败里，前两类是入口问题，后两类是深度问题。我一般会先集中解决前两类，因为它们是结构性问题。如果入口都不对，后面怎么优化都是白搭。

这里有一个特别实用的技巧。跑完第一轮真实任务之后，我会用一套大任务量的追问模板去进一步暴露问题。也就是连续追问多个问题，让模型在不同的追问路径下执行同一个 Skill。这种方法能很快测出 Skill 的稳定性，因为有些 Skill 在第一个问题里表现很好，但追问到第三个就开始跑偏了。接下来是第三步，用失败记录表手工优化。跑完真实任务之后，我会建一张简单的表。任务输入是什么，Skill 是否被正确触发，输出有什么问题，应该补到哪个文件里。

有一说一，这张表特别朴素，但效果出奇地好。因为它强迫你从一个具体的失败出发去修改 Skill，而不是凭空想象哪里需要优化。

在修改的过程中，我会把 skill-writing-guide 里的一些规范原则拿出来用。比如，在 SKILL.md 里不该写字段定义，字段定义要放到 references/schema.md 里。在 references 里不该写脚本逻辑，脚本逻辑要放到 scripts/ 下面。触发原则不能放在 references 里，必须放在 SKILL.md 的触发原则节。硬编码的关键词要从脚本里抽出来，放到 script-config.json 里。

这些规范听起来像是程序员的强迫症，但它们实际上解决了一个核心问题，职责混乱。一个文件如果同时负责触发判断和字段定义，改字段的时候很容易误触触发逻辑。拆开了之后，改起来就安全多了。

我重点补充的几个 references 文件大概是这样的。

interaction-rules.md 管交互逻辑。什么时候需要追问用户，什么时候可以直接执行，追问的话术模板是什么。这里有一个关键原则，规则必须可执行。模型看了之后能直接照做，而不是还要理解你的意图。比如，如果搜索关键词无结果，向用户汇报零结果并终止任务。这是一个可以直接执行的规则。但如果你写注意处理无结果的情况，模型就不知道该怎么办了。

output-structure.md 管输出格式。输出必须用 markdown 表格，表头必须包含这几列。字段顺序固定。字段缺失时如何处理。具体场景用什么分隔符。这些细节看起来很小，但说句实话，它们决定了输出的一致性。一致性对下游任务来说特别重要。

entity-scope.md 管实体范围。支持哪些实体类型，每个类型的定义是什么，字段解释，业务规则。比如实体的本地语言名称放在 entity_name_local 里，英文名称放在 entity_name_english 里，没有就留空。entity_type 必须是 industry_association、chamber、enterprise 之一。country_code 用 ISO 3166-1 alpha-2。这些标准引用不是为了炫技，而是为了让模型在输出时有明确的约束。

data-quality-rules.md 管数据可信度分级。90 到 100 分是政府登记系统直接确认，80 到 89 分是实体官网核心页面，65 到 79 分是上级组织目录，40 到 64 分是商业目录和聚合页，0 到 39 分是新闻、转载、论坛、缓存。同一字段出现冲突时，保留最高优先级来源的值，把其余值写入 conflicts，在 evidence_notes 里写明原因。这个分级标准听起来有点机械，但它解决了一个特别实际的问题。当你让模型去网上抓数据的时候，不同来源的可信度完全不一样，没有分级标准的话，模型会把可信的和不可信的混在一起给你。

scripts/ 下面的脚本也有一个规范。每个脚本要有 docstring，说明用途、输入输出和依赖。脚本必须能通过命令行直接调用。脚本不负责业务逻辑，业务逻辑由 SKILL.md 和 references 定义，脚本只负责执行。脚本里的可变参数要抽出来，放到 script-config.json 里。这个配置分离的思路特别重要，因为 Skill 部署到不同环境的时候，参数经常需要调整。如果参数硬编码在脚本里，改起来就很麻烦。

deployment-checklist.md 是一个容易被忽略的文件。但它特别实用。因为部署 Skills 的时候需要检查环境变量、依赖版本、模型可用性和权限。把它列成一个清单，每次部署前过一遍，能避免很多低级错误。

手工优化这个阶段大概会持续一到两周。不是每天都有时间做，但只要有新的真实任务，我就会把失败记录丢进表里，然后挑最频繁出现的问题去修改对应的文件。

这个过程里最重要的心态是，允许 Skill 不完美。有些失败是因为任务本身太模糊，不是 Skill 的问题。有些失败是因为参考资料不足，也不是 Skill 的问题。你要学会区分哪些失败是 Skill 可以解决的，哪些是需要用户补全信息的。这个区分能力只能靠自己慢慢练，没有捷径。

说实话，手工优化这个阶段挺磨人的。有时候改了一处，另一处又崩了。有时候你觉得已经覆盖得很全面了，新来一个任务又打回原型。但这也是最有价值的阶段。因为你在跟模型的真实行为对话，而不是跟自己的假设对话。到了第四步，用 SkillOpt 让优化变成可验证的工程动作。手工优化到一定程度之后，怎么说呢，会遇到一个天花板。你凭感觉改了一处，感觉它变好了，但怎么确认呢。这时候就需要工具介入了。

SkillOpt 的思路特别有意思。它不是让人类去判断修改好不好，而是让另一个模型去判断。具体来说，它把 Skill 当成一个可训练的外部状态。有一个 target model 负责执行任务，有一个 optimizer model 负责提出修改建议。然后在一个评估集上跑一轮，看修改后的表现有没有提升。

整个流程大概是六步。rollout，让 target model 用当前版本的 Skill 在评估集上跑一遍。reflect，让另一个模型分析失败案例，总结错误模式。aggregate，把多个失败案例的错误模式合并成具体的修改提案。select，从多个提案里挑最有价值的一批。update，把选中的修改写入 Skill 文件。gate，用一个门控模型评估这次更新后的表现，如果变差了就回滚。

这个流程里有两个我特别喜欢的细节。一个是 rejected-edit buffer，被拒掉的修改会被记录到缓冲区里，避免 optimizer 反复提出同一个错误。另一个是 slow update 和 meta update 的双层更新机制，高频的日常修改走快速通道，低频的结构性修改走元更新通道。

我在本地跑了一些实验。用 SearchQA 和 interview_practice 两个数据集做测试，大概是这样。

```powershell
cd E:\tools\SkillOpt
pip install -e .

python scripts/train.py `
  --config configs/searchqa/default.yaml `
  --split_dir data/searchqa_split `
  --num_epochs 2 `
  --batch_size 5 `
  --edit_budget 3
```

edit_budget 是每轮最多接受多少条编辑，我设的是 3，论文里默认是 4，我本地为了小样本实验收得更紧一点。

更推荐的写法是把覆盖项放到 cfg-options 里，这样改动和配置分离，比较干净。

实验结果大概是这样的。两轮训练下来，SearchQA 的 acc 从 71% 提升到 84%，interview_practice 从 74% 提升到 88%。这个提升看起来不错，但有意思的是，有一个特别重要的教训。第一轮我在评估集上取得了 96% 的通过率，当时我还挺得意。后来发现这个评估集太简单了，模型几乎不费力就能过。复杂指令的 acc 反而是 0，因为没有足够的数据覆盖那些边界情况。

这个教训直接改变了我对评估集的理解。评估集不能只是验证正确性，还要能暴露失败。如果评估集太容易通过，训练出来的 Skill 看起来很完美，但一遇到真实任务就原形毕露。所以评估集的设计要跟真实任务的分布对齐，要有足够的难度梯度，要能覆盖边界情况。

SkillOpt 解决的其实是第三层问题。手工优化解决的是我知道该改什么，SkillOpt 解决的是这个改动有没有带来真正的提升。它把我觉得该改变成了这个改动有没有通过验证。

这三层合起来，才像一个完整的 Skill 工作流。AI 生成结构，真实任务暴露失败，工具验证修改。

写到这里，我想聊一个稍微大一点的话题。以前我关心的是怎么写一个好 Skill。现在我更关心的是，怎么建立一个让 Skill 变好的循环。

以前我关心的是怎么写一个好 Skill。现在我更关心的是，怎么建立一个让 Skill 变好的循环。

这里面有一个挺有意思的对比。手艺人和工程师的区别。手艺人靠经验和直觉，每一锤都是感觉。工程师靠测量和反馈，每一次调整都有验证边界。我以前写 Skill 的时候更像手艺人，现在更像工程师。

不是说我变得多么理性了。不过话说回来，当 Skill 的规模变大、场景变多、迭代变快的时候，光靠手感是扛不住的。你需要有结构化的生成流程，有失败记录的追踪机制，有修改的验证闭环。这些东西听起来很工程化，但它们实际上是在保护你的直觉，让你的直觉有地方落地。

就像开头说的那个误触发的例子。如果我没有那个失败记录，我可能永远不知道问题出在 description 里的一个企业上。但如果我每一次失败都只是凭感觉改一下，没有记录，没有分类，没有验证，那我改一百次也还是在同一个坑里打转。

所以我现在写 Skill，会先让它犯错。故意让第一版不完美，故意把它丢进真实任务里栽跟头，故意用失败记录去逼自己面对那些 uncomfortable 的边界情况。只有当一个 Skill 第一次拒绝了一个看起来合理但没有带来提升的修改时，它才真正成熟了。
