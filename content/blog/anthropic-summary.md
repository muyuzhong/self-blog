这几天我把 Anthropic 最近几篇和 Agent 工程有关的文章集中读了一遍。

读之前，我对 Agent 的理解其实挺朴素：模型强一点，prompt 写好一点，工具接多一点，它应该就能干更多事。这个想法听起来没什么问题，但真正做过一阵子之后就会发现，很多问题不是模型“不够聪明”，而是我把工程部分想得太简单了。

所以这篇文章不是权威解读，也不是论文笔记。更准确地说，它是一个普通开发者读完之后的自我检查：我之前哪里做得太粗糙，后面可以怎么改。

## 先说结论

我最大的感受是：Agent 产品最后拼的不是“我接了多强的模型”，而是一些很朴素的工程能力。

比如：

- 工具是不是给得太多了；
- 上下文是不是被无意义信息塞满了；
- 有没有稳定的评估集；
- 出问题时能不能复现；
- 权限和安全默认值是不是靠谱；
- 多个 Agent 协作时有没有简单清楚的边界。

这些东西平时看起来没有模型参数、排行榜、prompt 技巧那么吸引人，但真的写项目时，最容易出问题的往往就是它们。

## 1. 工具不是越多越好

我以前做 Agent 的时候，有一个很自然的想法：工具越多，能力越强。

能接搜索就接搜索，能接数据库就接数据库，能接文件系统就接文件系统。看着工具列表越来越长，会有一种“这个 Agent 好像很强”的错觉。

但 Anthropic 的文章里反复提到一个问题：工具本身也是上下文成本。每个工具的名称、参数、描述、示例都会占 token。工具越多，模型不是更自由，而是更容易被干扰。

这点我很有体感。工具少的时候，模型虽然能做的事情有限，但选择路径比较清楚。工具一多，它经常会在几个相似工具之间乱选，或者明明只需要一个简单操作，却绕一大圈。

我现在更认可的做法是：

- 默认只暴露最常用、最稳定的工具；
- 复杂工具按需加载，不要一开始全塞进去；
- 工具描述少写空话，多给真实例子；
- 能用代码流程固定下来的步骤，不一定非要让模型每次自己想。

以前我总觉得“模型没选对工具”是模型的问题。现在看，很多时候是我给它的选择太多、太乱。

## 2. 没有评估，就只能靠感觉

这一点读完之后有点扎心。

我之前改 Agent 功能，很多时候就是跑几个自己熟悉的 case，看输出还可以，就觉得差不多了。这个流程很快，也很符合个人项目的节奏，但问题是它完全靠感觉。

感觉最大的问题是不可复现。

今天觉得结果不错，明天换个模型版本、改一段 prompt、加一个工具，输出突然变差了，我很难说清楚到底是哪一步引入的问题。

Anthropic 文章里提到的评估思路，让我意识到至少应该把测试分成两类：

- 一类是“不应该退步”的测试，比如旧功能还能不能正常跑；
- 一类是“能不能变强”的测试，比如新模型或新策略是否真的解决了新问题。

这听起来很基础，但我之前确实没有认真分开做。

以后我会给自己的 Agent 项目留一批固定样例。数量不用一开始就很多，但至少要能回答一个问题：我这次改动到底让系统变好了，还是只是看起来变好了？

## 3. 多 Agent 协作不一定要搞得很复杂

我以前一想到多 Agent 协作，脑子里就会出现一堆东西：任务队列、调度器、消息总线、状态同步、权限系统。

这些当然不是没用，但很容易一上来就过度设计。

Anthropic 文章里有个让我印象很深的点：有些多 Agent 协作并没有搞一个很复杂的中心系统，而是用 Git、锁文件、明确任务边界来协调。

这对我挺有启发。

因为很多个人项目或者早期项目，其实并不需要一套完整的分布式系统。只要做到下面几件事，已经能解决不少问题：

- 每个 Agent 只负责一块清楚的任务；
- 同一时间不要改同一批文件；
- 用 Git 记录每一步变化；
- 冲突就暴露出来，不要假装自动合并一切；
- 任务完成后留下能让下一个 Agent 看懂的说明。

这里最关键的不是“用不用 Git”，而是思路：先把边界做清楚，再谈自动化。

我以前太容易先想架构，后想边界。这个顺序其实反了。

## 4. 排行榜和 benchmark 要谨慎看

我以前看模型排行榜，多少会有点被数字牵着走。

A 比 B 高一点，就默认 A 更好。某个模型 benchmark 分数上来了，就觉得应该换。后来读到 Anthropic 关于评估环境影响的内容，才发现这个判断太粗糙。

模型表现不只和模型有关，也和运行环境、工具设置、上下文长度、评估方式有关。

有时候分数差一点，不一定说明模型本身强很多，可能只是环境配置、测试方式、任务拆分更适合它。

这对普通开发者来说也有用。我们不一定要做论文级 benchmark，但至少不要只看一个分数就做决定。

我现在更愿意这样选模型：

- 先拿自己的真实任务测；
- 看稳定性，而不是只看最好的一次输出；
- 记录失败样例，不只记录成功样例；
- 模型升级前后跑同一批用例；
- 成本、速度、稳定性一起看。

排行榜可以参考，但不能替代自己的测试。

## 5. 写代码时，一个“挑刺的人”很有用

Anthropic 提到过类似 Writer + Evaluator 的模式：一个负责生成，一个负责检查。

这个模式我之前也零散用过，但没有把它当成固定流程。

现在想想，它特别适合开发场景。因为模型写代码时经常会出现一种情况：第一眼看上去很完整，文件也改了，逻辑也通了，但细节里藏着问题。

比如：

- 错误分支没处理；
- 类型边界没考虑；
- 测试只覆盖了最顺的路径；
- 某个旧行为被顺手改坏了；
- 文案和真实行为对不上。

如果只让一个模型从头写到尾，它很容易对自己的方案太自信。让另一个角色专门检查，哪怕只是按清单挑问题，也能发现很多低级错误。

这件事对我自己的启发是：以后不要把“生成代码”和“检查代码”混在一个脑子里完成。哪怕没有多个模型，也应该在流程上拆开。

先写，再审。先实现，再用另一套标准挑毛病。

## 6. 安全默认值比弹窗更重要

这一点我以前想得也比较简单。

我会觉得：危险操作让用户确认一下，不就安全了吗？

但实际情况是，大多数人看到确认框并不会认真读。尤其是在开发工具里，弹窗多了以后，用户只会形成肌肉记忆：点确定，继续干活。

所以“让用户确认”不等于安全。

更靠谱的方式应该是把默认行为设计得保守一点：

- 默认不要碰敏感文件；
- 默认不要执行不可逆操作；
- 默认把高风险命令拦下来；
- 真的需要放开时，再让用户明确授权；
- 授权文案要说清楚风险，而不是只写“是否继续”。

这和我以前的想法不太一样。我以前是先假设 Agent 可以做很多事，再用确认框兜底。现在我更倾向于反过来：默认少做，只在必要时放开。

## 7. Agent 运行时要有边界感

Anthropic 关于运行时架构的文章里，有一个我觉得很重要的点：不要把所有东西搅在一起。

会话记录、模型推理、工具执行、沙箱环境、权限管理，这些东西最好有清楚边界。

我以前写原型时经常偷懒：一个函数里既拼 prompt，又调用模型，又读文件，又写结果。短期看很快，长期看会非常难调。

因为一旦出问题，你很难判断问题到底在哪：

- 是 prompt 没说清楚？
- 是模型输出不稳定？
- 是工具返回格式变了？
- 是上下文里混进了脏数据？
- 是某个执行环境的权限不一致？

如果边界不清楚，排查问题就只能靠猜。

我现在觉得，即使是个人项目，也至少应该把几个层次分开：

- 输入和会话记录；
- 模型决策；
- 工具调用；
- 执行结果；
- 最终输出。

不一定一开始就设计得很重，但脑子里要知道每层负责什么。

## 8. “模型变笨了”可能不是一个问题

我自己也遇到过类似情况：某天突然觉得模型输出没之前好了。

第一反应通常是怀疑模型。是不是版本变了？是不是供应商退步了？是不是 prompt 不适配了？

但 Anthropic 的复盘提醒我，有时候这种“变差”不是一个大问题，而是几个小问题叠在一起。

比如：

- 默认参数变了；
- 上下文清理策略变了；
- 系统提示词多了一段限制；
- 工具返回内容变长了；
- 依赖版本更新后格式不一样了。

单独看每个问题都不明显，但叠起来，用户体感就是“怎么突然不好用了”。

这对排查问题很有帮助。以后遇到类似情况，我会先把变量列出来，一个一个排，而不是直接怪模型。

## 我读完之后准备怎么改

如果只停留在“这几篇文章挺有启发”，其实没什么用。对我来说，更重要的是把它变成后面的开发习惯。

我准备先做几件很小的事：

1. 给自己的 Agent 项目整理一批固定测试样例。
2. 工具列表做减法，不再一股脑全暴露。
3. 给每个工具补 1 到 3 个真实调用例子。
4. 模型升级前后跑同一批用例做对比。
5. 把生成和检查拆成两个步骤。
6. 对高风险操作设置更保守的默认值。
7. 代码里把会话、推理、工具执行的边界拆清楚一点。

这些都不是很酷的事情，也不是什么新概念。但我现在越来越觉得，真正能把 Agent 做稳定的，往往就是这些不太起眼的工程细节。

## 最后

读完 Anthropic 这些文章后，我最大的变化不是学会了某个具体技巧，而是对 Agent 工程的期待变现实了。

以前我更关注“模型能不能一次做对”。现在我更关注“如果它这次没做对，我有没有办法发现、复现、修掉，并且防止下次再发生”。

这个心态变化挺重要的。

因为对普通开发者来说，我们不一定能训练模型，也不一定能控制模型发布节奏。但我们能控制自己的工具设计、上下文管理、评估流程和默认行为。

这些东西做好了，模型能力才真的能落到产品里。

我现在还在踩坑，只是比之前更清楚：很多坑不是靠再写一段 prompt 填平的，而是要靠更扎实的工程习惯慢慢补上。
