> **TL;DR**
>
> Agent 产品的下限不取决于模型，而取决于工程：工具够不够节制、上下文够不够干净、评估能不能复现、默认行为够不够保守。这篇文章按主题整理了我读完 Anthropic 几篇相关文章后的反思，以及我接下来准备做的几件小事。

这几天我把 Anthropic 最近发的几篇 Agent 工程文章集中读完了。

读之前，我对 Agent 的认知挺朴素：**模型再强一点、prompt 再细一点、工具再多接一点，能力就该再涨一截**。听起来没什么问题，但真正做过一阵子后会发现，很多体验问题并不是模型「不够聪明」，而是我把工程那一层想得太简单了。

所以这篇不是论文笔记，也不是权威解读。它更像是我对自己的一次审视——**哪些地方做得太粗糙，哪些地方下一步可以更扎实**。

## 先说结论

我最大的感受可以浓缩成一句话：

> Agent 产品最后拼的，不是「我接了多强的模型」，而是一些非常朴素的工程能力。

具体来说，最常出问题的几件事，往往都不在模型本身：

- 工具是不是给得太多了
- 上下文里是不是塞满了无意义的信息
- 有没有一套能复现的评估集
- 出问题时能不能定位到原因
- 权限和默认值是不是够保守
- 多个 Agent 协作时，边界是不是清楚

这几条单看都很无聊，但真正写项目时，最容易翻车的也正是它们。

## 工具不是越多越好

我以前做 Agent 的时候，有一种很自然的冲动：**工具越多，能力越强**。

能接搜索就接搜索，能接数据库就接数据库，能接文件系统就接文件系统。看着工具列表越拉越长，会有一种「这个 Agent 好像很厉害」的错觉。

但 Anthropic 反复强调一点——**工具本身就是上下文成本**。每个工具的名称、参数、描述、示例都在占 token。工具越多，模型不是更自由，而是更容易被干扰。

这点我很有体感：

- 工具少时，模型能做的事有限，但路径清晰
- 工具多时，它经常在几个相似工具之间反复横跳，或者明明只需要一步操作，却绕一大圈

我现在更认可的做法是：

- 默认只暴露最常用、最稳定的工具
- 复杂工具按需加载，不要一上来就全塞进去
- 工具描述少写空话，**多给真实的调用示例**
- 能用代码流程固定下来的步骤，不必让模型每次都自己想

> 以前我总觉得「模型没选对工具」是模型的问题。现在看，**很多时候是我给它的选择太多、太乱**。

## 没有评估，就只能靠感觉

这一点读完之后，挺扎心。

我以前改 Agent 功能，多半就是跑几个自己熟的 case，输出还行，就觉得差不多了。这个流程很快、很贴合个人项目的节奏，但问题也很明显——**它完全靠感觉**。

感觉最大的毛病是不可复现：

> 今天觉得结果不错，明天换个模型版本、改一段 prompt、加一个工具，输出突然就变差了。我很难说清楚到底是哪一步引入的问题。

Anthropic 文章里提到的评估思路提醒我，至少应该把测试分成两类：

- 一类是「**不应该退步**」的测试——旧功能还能不能正常跑
- 一类是「**能不能变强**」的测试——新模型或新策略是否真的解决了新问题

听起来基础，但我之前确实没认真区分。

以后我会给自己的 Agent 项目留一批固定样例。数量不需要一开始就很多，但至少要能回答一个问题：

**这次改动到底让系统变好了，还是只是看起来变好了？**

## 多 Agent 协作不一定要搞得很复杂

我以前一想到多 Agent 协作，脑子里就会蹦出一堆东西：任务队列、调度器、消息总线、状态同步、权限系统……

这些当然不是没用，但很容易**一开始就过度设计**。

Anthropic 文章里有个让我印象很深的点：有些多 Agent 协作并不需要一个复杂的中心系统，**用 Git、锁文件、明确的任务边界**就能协调起来。

这对我挺有启发——很多个人项目或早期项目，根本不需要一套完整的分布式系统。只要做到下面几件事，已经能解决不少问题：

- 每个 Agent 只负责一块清楚的任务
- 同一时间不要改同一批文件
- 用 Git 记录每一步变化
- 冲突就暴露出来，不要假装自动合并
- 任务完成后，留下能让下一个 Agent 看懂的说明

关键不是「用不用 Git」，**关键是先把边界做清楚，再谈自动化**。

我以前的顺序刚好反了——总是先想架构，再想边界。

## 排行榜和 benchmark 要谨慎看

我以前看模型排行榜，多少会被数字牵着走：A 比 B 高一点，就默认 A 更好；某个模型 benchmark 上来了，就觉得该换。

读完 Anthropic 关于评估环境影响的内容后，我意识到这个判断太粗糙。

> **模型表现不只跟模型有关，也跟运行环境、工具配置、上下文长度、评估方式有关。**

有时候分数差一点，未必说明模型本身强很多，可能只是某种环境配置、测试方式、任务拆分对它更友好。

对普通开发者来说，结论很简单：**不要只看一个数字就做决定**。

我现在更倾向于这样选模型：

- 先拿自己的真实任务测
- 看稳定性，而不是只看最好的一次输出
- 记录失败样例，不只记录成功样例
- 模型升级前后，跑同一批用例做对比
- 成本、速度、稳定性一起看

排行榜可以参考，**但不能替代自己的测试**。

## 写代码时，需要一个「挑刺的人」

Anthropic 提到过类似 Writer + Evaluator 的模式：一个负责生成，一个负责检查。

这个模式我以前零星用过，但没把它当成固定流程。

现在想想，它特别适合开发场景。因为模型写代码时经常有一种典型表现：**第一眼看上去很完整，文件改了，逻辑也通了，但细节里藏着问题**。

比如：

- 错误分支没处理
- 类型边界没考虑
- 测试只覆盖了最顺的路径
- 某个旧行为被顺手改坏
- 文案和真实行为对不上

如果让一个模型从头写到尾，它很容易对自己的方案过度自信。让另一个角色专门检查——哪怕只是按清单挑问题——也能扫出很多低级错误。

> 以后不要把「生成代码」和「检查代码」放在同一个脑子里完成。哪怕没有多个模型，也要在流程上拆开。
>
> **先写，再审；先实现，再用另一套标准挑毛病。**

## 安全默认值比弹窗更重要

这一点我以前想得也比较简单——**危险操作让用户确认一下，不就安全了吗？**

但实际情况是：大多数人看到确认框并不会认真读。尤其是在开发工具里，弹窗多了，用户只会形成肌肉记忆——**点确定，继续干活**。

所以「让用户确认」并不等于安全。

更靠谱的方式是把默认行为本身设计得保守：

- 默认不要碰敏感文件
- 默认不要执行不可逆操作
- 默认把高风险命令拦下来
- 真的需要放开时，再让用户明确授权
- 授权文案要说清楚风险，而不是只写「是否继续」

我以前的思路是：先假设 Agent 可以做很多事，再用确认框兜底。

现在我更倾向于反过来：**默认少做，只在必要时放开**。

## Agent 运行时要有边界感

Anthropic 关于运行时架构的文章里，有一个我觉得很重要的点——**不要把所有东西搅在一起**。

会话记录、模型推理、工具执行、沙箱环境、权限管理，这几层最好有清楚的边界。

我以前写原型时经常偷懒：一个函数里既拼 prompt，又调模型，又读文件，又写结果。短期看很快，长期看会非常难调。

因为一旦出问题，你很难判断它到底卡在哪：

- 是 prompt 没说清楚？
- 是模型输出不稳定？
- 是工具返回格式变了？
- 是上下文里混进了脏数据？
- 是某个执行环境的权限不一致？

**边界不清楚，排查就只能靠猜**。

我现在觉得，即使是个人项目，也至少要在脑子里把几层分开：

- **输入层**：用户输入、会话历史
- **决策层**：模型推理、工具选择
- **执行层**：工具调用、副作用
- **输出层**：最终结果、回填上下文

不一定一上来就设计得多重，但每一层负责什么，要心里有数。

## 「模型变笨了」往往不是一个问题

我自己也遇到过：某天突然觉得模型输出没以前好用了。

第一反应通常是怀疑模型——是不是版本变了？是不是供应商退步了？是不是 prompt 不适配了？

但 Anthropic 的复盘提醒我：有时候这种「变差」**不是一个大问题，而是几个小问题叠在一起**。

比如：

- 默认参数变了
- 上下文清理策略变了
- 系统提示词多了一段限制
- 工具返回内容变长了
- 依赖版本更新后格式不一样了

每一项单看都不明显，叠起来，用户体感就是「怎么突然不好用了」。

这对排查问题很有用。以后遇到类似情况，**先把变量列出来，一个一个排，而不是直接怪模型**。

## 我准备怎么改

读完文章如果只停留在「挺有启发」，其实没什么用。对我来说，更有意义的是把它落到下一步的开发习惯里。

我准备先做几件不大的事：

1. 给现有的 Agent 项目整理一批固定测试样例
2. 工具列表做减法，不再一股脑全暴露
3. 给每个工具补 1 ~ 3 个真实调用示例
4. 模型升级前后，跑同一批用例做对比
5. 把生成和检查拆成两个步骤
6. 高风险操作设置更保守的默认值
7. 代码里把会话、推理、工具执行的边界拆清楚

这些都不是什么炫的事情，也算不上新概念。但**真正能让 Agent 跑稳的，往往就是这些不起眼的工程细节**。

## 写在最后

读完这几篇文章，我最大的变化不是学会了某个具体技巧，而是对 Agent 工程的期待**变现实了**。

> 以前我更关注：「**模型能不能一次做对**」。
>
> 现在我更关注：「**如果它这次没做对，我有没有办法发现、复现、修掉，并且防止下次再发生**」。

这个心态转变挺重要。

因为对普通开发者来说，我们不一定能训练模型，也控制不了模型发布节奏。但我们能控制的——工具设计、上下文管理、评估流程、默认行为——其实并不少。

这些做扎实了，模型能力才真的能落到产品里。

我现在还在踩坑，只是比之前更清楚一件事：**很多坑不是再写一段 prompt 就能填平的，得靠更扎实的工程习惯慢慢补上**。
