> **TL;DR**
>
> 大多数 Multi-Agent 方案都在追求「每个 Agent 都很强」，结果成本炸了、协调崩了、落地遥遥无期。我试了一种反过来的路子——强模型只当军师负责思考和规划，弱模型当武将负责执行，遇阻时再回头请示。效果比我预期的好太多。

故事是这样的。

上个月我在做一个 Agent 项目，要处理一堆杂活——读文件、搜资料、写代码、跑测试、生成报告。一开始我用了单 Agent 方案，把所有工具一股脑塞给 GPT-4o。能用，但每次跑一遍的成本让我肉疼，而且它经常在简单任务上用力过猛，杀鸡用牛刀。

然后我试了 Multi-Agent。结果呢？每个 Agent 都用强模型，成本直接翻了三四倍；Agent 之间互相扯皮，一个说「这个文件我来改」，另一个说「不对，我已经改了」；更要命的是，协调逻辑比业务逻辑还复杂。

有天晚上我在 debug 一个 Agent 间消息传递的 bug，修到凌晨两点，突然脑子里冒出一个画面——

**诸葛亮坐在帐中摇扇子，关羽张飞在外面砍人。**

诸葛亮不会自己提刀上阵，但他告诉关张什么时候该打、往哪打、遇到埋伏怎么办。关张也不会坐下来研究什么天下大势，他们就是听令行事，干就完了。遇到搞不定的局面，回头问军师。

这不就是我要的东西吗？

## 军师型架构到底是什么

给它起了个名字，叫**军师型 Multi-Agent**。

核心思路极其简单，一句话说清楚：

> **强模型只思考不行动，弱模型只行动不思考，遇阻时弱模型向强模型求援。**

拆开来看就是三层角色：

**军师（Strategist）**
- 用最强的模型，比如 Claude Opus、GPT-4o
- 不直接调用任何工具，不执行任何操作
- 只做三件事：制定计划、拆解任务、回答武将的求助
- 相当于大脑，只出主意不动手

**武将（Executor）**
- 用便宜的弱模型，比如 Claude Haiku、GPT-4o-mini、Qwen-7B
- 接收军师的任务，直接调用工具去执行
- 能做就做，做不了就回头找军师
- 相当于手脚，只干活不规划

**斥候（Reporter）**
- 把武将的执行结果汇报给军师
- 可以是独立的轻量 Agent，也可以就是一个信息格式化函数
- 核心作用是帮军师过滤噪音，只看关键信息

整个流程就长这样：

```
用户请求 → 军师思考出计划 → 拆成小任务给武将 → 武将执行
     ↑                                          ↓
     ← ← ← 遇阻求援 / 完成汇报 ← ← ← ← ← ←
```

没有消息总线，没有任务队列，没有复杂的调度器。就是一个最朴素的请求-响应循环，加上一个「做不了就问」的兜底机制。

## 为什么反直觉，但确实管用

大多数人第一次听到这个架构，反应都是：弱模型能干啥？最后还不是强模型兜底？

这话对了一半。弱模型确实干不了特别难的事，但问题在于——**大多数任务根本就不难**。

我统计了一下自己那个项目里 Agent 执行的任务分布：

- 读一个文件、提取关键信息——弱模型就能做，准确率 95%+
- 按模板写一段代码——弱模型就能做
- 跑一条命令、收集输出——根本不需要模型，脚本就行
- 在几个文件里做字符串替换——弱模型轻松搞定
- 分析一段复杂逻辑、做架构决策——这才需要强模型

结果就是：**大约 80% 的任务，弱模型完全胜任。** 剩下 20%，才是强模型出场的时候。

而这个分布，我后来发现不是个例。几乎所有的 Agent 项目，任务难度都符合长尾分布——简单的占绝大多数，真正需要「深度思考」的极少。

所以军师型架构真正做的事情，不是让弱模型去扛难活，而是**别让强模型浪费在简单任务上**。

这就像一个公司，CEO 不会自己去贴发票。不是贴不了，是不值得。CEO 的时间应该花在战略决策上，贴发票这种事交给实习生就成。

## 和现有架构的区别

市场上主流的 Multi-Agent 架构大概有这几种，我来逐个对比一下。

### 对比一：对等协作型（AutoGen 风格）

所有 Agent 地位平等，互相发消息、讨论、协作。听起来很民主，但实际跑起来有几个问题：

- 每个 Agent 都用强模型，成本很高
- Agent 之间容易陷入「无限讨论」的死循环
- 没有明确的决策者，遇到分歧不知道听谁的
- 消息噪音大，每次对话都在消耗 token

军师型直接砍掉了对等讨论这个环节。军师说了算，武将听令。不需要协商，不需要投票，不需要共识。听起来独裁，但效率就是高。

### 对比二：层级调度型（CrewAI 风格）

有一个 Manager Agent 负责分配任务，Worker Agent 负责执行。这已经比较接近军师型了，但有一个关键区别：

**CrewAI 的 Manager 通常也参与执行。** 它既规划又干活，角色边界模糊。结果就是 Manager 经常自己去干本该分配出去的活——因为强模型有一种倾向，觉得「我自己来更快更靠谱」。

军师型强制军师不执行，从架构层面杜绝了这个问题。军师的工具列表是空的，它想干也干不了。这种硬约束比任何 prompt 劝说都管用。

### 对比三：Plan-and-Execute（LangGraph 风格）

先让强模型出一个完整计划，再让执行器按计划一步步来。这思路很对，但有个致命问题：

**计划赶不上变化。**

执行过程中一旦遇到计划外的情况——文件格式不对、API 返回了意外结果、某个依赖缺失——执行器就傻了。它没有能力应对计划外的状况，只能硬着头皮继续或者直接失败。

军师型解决了这个问题：武将遇到计划外情况，直接回头问军师。军师根据新信息调整策略，给武将新的指令。这是一个**动态适应**的过程，不是一份写死的手册。

## 落地实操：怎么搭一个军师型系统

说完了为什么，说说怎么做。我用自己的项目为例，把关键步骤拆开讲。

### 第一步：选模型

军师和武将的模型选择，直接决定了整个系统的性价比。

**军师模型选择原则：**

选最强、最稳的。不用考虑成本，因为军师调用频率低——只在初始规划和遇阻时才动。一个任务跑下来，军师可能只被调用 2-3 次，但每一次都很关键。

我的选择：Claude Opus 4 或 GPT-4o。不用省钱。

**武将模型选择原则：**

选最便宜、最快的。武将调用频率极高——每一步执行都是一次调用。但要求也没那么高，只要能读懂指令、调用工具、返回结构化结果就行。

我的选择：Claude Haiku 3.5 或 GPT-4o-mini。成本大约是强模型的 1/20。

一个具体数字：我那个项目，全用 GPT-4o 单次运行成本约 0.8 美元，换成军师型架构后降到了 0.12 美元。一个字，香。

### 第二步：定义军师的 Prompt

军师的 System Prompt 是整个架构的灵魂。核心要素：

```
你是一个军师。你的职责是：
1. 分析用户需求，制定执行计划
2. 将计划拆解为可独立执行的小任务
3. 当武将求助时，分析问题并给出新指令

你绝对不能：
- 直接调用任何工具
- 直接执行任何操作
- 跳过规划直接给结果

你的输出格式：
- 新任务时：输出任务列表，每个任务包含目标、步骤、预期结果
- 求助时：分析原因，调整方案，输出新的执行指令
- 全部完成时：输出最终总结
```

几个关键设计点：

**「绝对不能执行」要反复强调。** 强模型很聪明，如果你只说一次「不要执行」，它有时候还是会忍不住绕过限制自己动手。在 prompt 里至少说两遍，再加上工具列表为空的硬约束，基本就稳了。

**输出格式要结构化。** 军师输出的任务描述，就是武将的输入。格式越清晰，武将的执行准确率越高。我用的格式是 JSON，每个任务包含 `objective`、`steps`、`expected_output` 三个字段。

**求助处理要有优先级。** 不是所有求助都值得军师重新规划。有些小问题，军师只需要给一个简短的提示就行。我把求助分成了三级：小问题（一句话指导）、中问题（调整步骤）、大问题（重新规划），军师根据情况选择。

### 第三步：定义武将的 Prompt

武将的 Prompt 要简单到弱模型也能完全理解：

```
你是一个执行者。你的任务是：
1. 按照收到的任务指令执行
2. 使用可用工具完成每个步骤
3. 如果遇到无法解决的问题，向军师求助

求助格式：
{
  "status": "blocked",
  "reason": "具体遇到了什么问题",
  "attempted": "你已经尝试了什么",
  "context": "当前的执行状态"
}

完成格式：
{
  "status": "done",
  "result": "执行结果",
  "artifacts": "产出的文件或数据"
}
```

武将的 prompt 越短越好。弱模型的上下文窗口是宝贵资源，不要塞一堆有的没的。核心就三件事：**执行、求助、汇报**。

### 第四步：实现求助机制

这是整个架构最核心的机制。求助不是简单的「做不了就问」，而是要有一套清晰的规则，避免武将动不动就找军师——那样成本又会飙上去。

我设了几个阈值：

**尝试次数阈值：** 同一个问题最多自己尝试 2 次。2 次都失败，立即求助。不要浪费 token 在无效重试上。

**错误类型判断：** 有些错误武将自己能解决——比如文件路径写错了、参数格式不对，这些属于「小问题」，自己修就行。但如果是逻辑错误、理解偏差、缺少关键信息，这些属于「真做不了」，必须求助。

**进度汇报间隔：** 每完成 3 个步骤，武将要主动向军师汇报一次进度。这不是求助，是让军师保持对全局的感知，必要时提前干预。

用代码实现大概长这样：

```python
async def run_executor(task, max_retries=2):
    for attempt in range(max_retries):
        result = await executor_agent.run(task)
        
        if result.status == "done":
            return result
        
        if result.status == "blocked":
            # 判断是否可以自行修复
            if is_minor_error(result.reason) and attempt < max_retries - 1:
                task = auto_fix(task, result.reason)
                continue
            else:
                # 向军师求助
                guidance = await strategist_agent.run(
                    f"武将遇阻：{result.reason}\n已尝试：{result.attempted}\n请给出新的指令。"
                )
                task = guidance.new_task
                continue
    
    return result
```

### 第五步：处理上下文传递

多 Agent 系统最容易翻车的地方之一，就是上下文丢失。军师不知道武将干了什么，武将不知道军师之前的规划，结果就是各干各的。

我的做法是维护一个**共享的任务状态文档**，不是传统意义上的共享记忆，而是一个简单的 JSON 文件：

```json
{
  "plan": "军师的原始计划",
  "completed": ["已完成的任务列表"],
  "current": "当前正在执行的任务",
  "blocked": ["被阻塞的任务和原因"],
  "notes": "军师和武将都可以追加的备注"
}
```

军师每次规划后更新 `plan`，武将每完成一步更新 `completed`，遇阻时更新 `blocked`。下次任何一方被调用时，先读这个文件，就拥有了完整的全局视角。

这比在对话历史里传一堆消息高效得多。消息历史会越来越长、越来越脏，而状态文档永远只有关键信息。

## 实际效果

用了这个架构之后，最直观的感受就三个：

**成本降了。** 原来全用强模型跑一个完整任务流，成本大概 0.8 美元。现在军师型架构下，平均 0.1-0.15 美元。降了 80%+。

**速度提了。** 弱模型响应速度比强模型快 3-5 倍。那些不需要深度思考的步骤，以前等强模型磨蹭半天，现在弱模型秒回。

**协调顺了。** 没有对等协作的消息风暴，没有 Manager 亲力亲为的越界，没有 Plan-and-Execute 遇到变化就崩。军师说了算，武将听令，做不了就问，就这么简单。

但也不是没有坑。

## 踩过的坑

**坑一：弱模型有时候太弱了。**

有些任务看起来简单，但弱模型就是做不好。比如需要精确匹配 JSON 格式的输出，弱模型偶尔会多一个逗号、少一个引号。我现在的解法是在武将和工具之间加一层格式校验，出错就自动重试一次，不行再求助。

**坑二：军师被求助太频繁。**

一开始我的求助阈值设得太低，武将动不动就找军师。一个任务跑下来，军师被调用了十几次，比全用强模型还贵。后来调整了策略——只有武将自己尝试过但确实搞不定的问题才求助，军师调用次数降到了 2-3 次。

**坑三：状态文档的同步问题。**

如果武将并行执行多个任务，状态文档的并发写入会出问题。我的项目规模不大，直接用文件锁解决了。如果规模更大，可能需要换成真正的数据库或消息队列。但我想说的是——**先别急着上重型基础设施**。文件锁不够用再升级，不要一开始就搞一套分布式系统出来。

**坑四：军师的规划质量是上限。**

整个系统的天花板取决于军师。如果军师的规划本身就是错的，武将再怎么执行也没用。所以军师的 prompt 设计和模型选择一定不能省。这一层值得花时间打磨。

## 什么时候该用，什么时候不该用

军师型架构不是万能的。它最适合的场景是：

- **任务以执行为主，决策为辅。** 大部分步骤是调用工具、处理数据、读写文件，少量步骤需要深度思考。
- **成本敏感。** 不是所有人都能承受全量强模型的调用费用。
- **需要动态适应。** 执行过程中可能遇到计划外的情况，需要实时调整。

不适合的场景：

- **所有任务都很简单。** 这种直接用弱模型单 Agent 就够了，不需要架构。
- **所有任务都很难。** 如果弱模型压根干不了活，军师型架构就退化成了单 Agent，只是多了一层没必要的包装。
- **需要多个 Agent 并行协作。** 军师型本质是串行的——一个武将做完再给下一个。虽然可以多起几个武将并行，但协调复杂度会迅速上升。真到了那一步，可能需要更成熟的框架。

## 和学术研究的对照

写这篇文章的时候，我发现军师型的核心思路，和学术界一些研究方向不谋而合。

北航和中国电信合作的一篇论文《Weak-Driven Learning》提出了一个反直觉的观点——弱模型可以帮助强模型变得更强。他们的场景是训练而非推理，但底层逻辑是相通的：**弱模型的价值不在于它本身的能力，而在于它的「不确定性」暴露了问题的边界。**

在我们的军师型架构里，弱模型的求助信号其实也在做类似的事——它标注了「这个任务超出了弱模型的能力边界」，相当于给军师提供了一块精准的注意力地图。军师不需要关注所有步骤，只需要关注那些弱模型搞不定的关键节点。

Anthropic 在他们关于 Agent 工程的文章里也提到过 Writer + Evaluator 模式——一个负责生成，一个负责审查。军师型可以看作是这个模式的扩展：不只是生成+审查，而是规划+执行+求助的三层结构。

OpenAI 的 Plan-and-Execute 论文也讨论了类似的问题，他们的解法是用 LLM 做规划器、用 LLM 或脚本做执行器。军师型和它的核心区别在于——我们加了**动态求助**这个环节，让执行器在遇到计划外情况时不会直接失败，而是可以请求重新规划。

## 最后说几句

军师型 Multi-Agent 不是什么新架构，它只是把一个很朴素的道理用到了 Agent 设计上：

**好钢用在刀刃上。**

强模型很贵，但绝大多数任务不值得它出手。弱模型很便宜，但在关键时刻兜不住。把它们结合起来，各司其职，就是性价比最高的方案。

这个思路不是我一个人的发现，很多做 Agent 的朋友私下都在用类似的模式。只是大家叫法不一样——有的叫 Planner-Executor，有的叫 Manager-Worker，有的叫 Supervisor-Agent。但核心都是同一件事：**让聪明人思考，让干活的人干活。**

我叫它「军师型」，因为这个名字最直观。诸葛亮不提刀，关张不摇扇。各干各的，遇到麻烦再合计。

如果你也在做 Agent 项目，而且被成本和协调复杂度困扰，不妨试试这个路子。实现起来比你想的简单，效果比你想的好。

至少，比让一群强模型互相吵架强多了。
