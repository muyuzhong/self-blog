# 记忆与上下文：档案馆里那盏灯

> **引言**
>
> 城里有一座档案馆。每场审判、每次修桥、每份契约都会被送到这里。新来的书记员以为，法官办案时只要把档案馆搬到法庭，真相就会自己显出来。
>
> 老馆员拦住了他。她打开一盏灯，只照亮几只木箱：一箱是原始证据，一箱是上一场审理留下的记录，一箱是多年积累的判例。她说："法官需要看见相关证据，不需要被所有纸张淹没。证据要完整保存，呈给法官的内容要克制。"
>
> 书记员问："那谁来决定哪一页上桌？"
>
> 老馆员把灯往前推了推："这就是档案馆真正的工作。"
>
> Agent 的记忆与上下文子系统，做的正是这件事。

---

> **TL;DR**
>
> 记忆回答"系统过去知道什么"，上下文回答"本轮让模型看到什么"。记忆库追求完整、来源和可追溯；上下文投影追求相关、紧凑和预算可控。把两者混成一团，模型会在无关历史里迷路，也会把未经验证的推断当成长期事实。

---

## 1. 记忆和上下文不是同一件事

记忆可以跨会话、跨项目保存很久。上下文只存在于一次模型调用里，受窗口、预算和任务目标限制。

这条边界很关键：

- 保存了信息，不代表模型本轮应该看到它。
- 模型看到了信息，不代表系统应该永久保存它。
- 工具返回了完整证据，不代表要把原文全塞进上下文。

可靠系统会分出两种视图。证据视图保存完整工具结果、原始会话、版本和来源，用于审计和复现。模型视图只给当前推理需要的摘要、关键片段和引用位置。

当你为了省 token 直接删掉原始证据，后续就无法复查模型到底基于什么判断。当你为了完整性把所有历史塞给模型，关键约束又会被噪声淹没。

## 2. 分层记忆解决生命周期问题

Agent 需要至少三层记忆。

工作记忆放本轮输入、最近消息、当前工具结果和即时状态。它最快，也最容易被窗口挤满。

短期记忆保存会话摘要、最近任务进度和临时决策。它让系统能恢复近期工作，而不用每次从头读完整历史。

长期记忆保存用户偏好、项目规则、稳定事实、可复用经验。它有长期价值，但必须经过写入决策。

向量索引不属于第四种记忆。它只是检索入口，指向权威原文。索引和原文冲突时，应相信原文并重建索引。

记忆写入不能太随意。模型提出的猜测、一次失败尝试、临时命令输出，都不应自动变成长期事实。长期记忆最好区分事实、推断和经验规则，并记录来源、时间、置信度和适用范围。

## 3. 检索要找到相关，也要判断可信

只做向量搜索不够。语义相近不代表事实相关，更不代表内容仍然正确。

一次实用检索通常先按用户、项目和权限缩小范围，再结合关键词、标签、结构化字段和向量相似度召回候选，最后按相关性、重要性、近因、置信度和时效性重排。

进入上下文前，还要问几件事：

- 这条记忆属于当前用户和项目吗？
- 它有没有过期或被新版本替代？
- 它是事实、推断，还是经验？
- 它的原始证据在哪里？
- 它和其他记忆是否冲突？

检索结果需要可解释。系统用一条记忆影响模型决策时，工程师要能看到它为什么被召回、来自哪里、何时验证过。否则模型一次奇怪选择背后，可能藏着一条早就污染的长期记忆。

## 4. 上下文组装是一份投影

上下文组装不是字符串拼接。一次模型调用会争夺同一个窗口：系统指令、工具 Schema、当前请求、任务状态、最近历史、检索记忆、工具观察、输出预留空间。

组装引擎要先判断当前任务需要哪些信息，再并行检索候选内容，最后按优先级装配。常见顺序是：安全约束、当前请求、核心目标、必要项目规则、最近有效行动、相关长期记忆、参考资料。

系统还要划出保护区。安全指令、当前用户请求、原始目标、未完成工具调用信息不能被普通裁剪挤掉。历史、参考资料和长工具输出可以按预算裁剪或摘要。

最成熟的做法，是把组装结果本身也记录下来：选了哪些记忆、丢了哪些候选、为什么裁剪、每个来源占多少 token、是否命中缓存。没有这份 context trace，团队很难判断问题出在检索、组装，还是模型使用信息的能力。

## 写在最后

多年后，老馆员退休。新馆员接过那盏灯，发现灯罩上刻着一句小字：照亮该看的，保存不能丢的。

他终于明白，档案馆的本事不在于纸多，而在于分得清哪张纸现在该上桌，哪张纸该完整封存，哪张纸只是书记员的猜测，不能盖上事实的印章。

记忆与上下文也是这样。好的 Harness 不靠把过去全塞给模型来假装连续，它靠保存证据、筛选相关、标明来源、控制预算，让模型每一次思考都站在足够短、也足够真的材料上。

那盏灯不替法官断案。它只让法官看见该看的东西。
