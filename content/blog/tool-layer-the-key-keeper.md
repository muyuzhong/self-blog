# 工具层设计：给行动上锁的人

> **引言**
>
> 镇上的钟表匠有一间很大的工具室。里面有游标卡尺、铣刀、炉火、印章和能打开每个仓库的钥匙。学徒第一次进去时很兴奋，他觉得只要手里有足够多的工具，所有钟都能修好。
>
> 工具室门口坐着一位管钥匙的人。她不给每个人整串钥匙，只问三件事：你要修哪座钟，要拿哪件工具，拿走之后会影响什么。拿锉刀的人可以直接登记，拿炉火的人要有人在旁边看着，拿仓库钥匙的人必须写清用途和归还时间。
>
> 学徒抱怨她太慢。钟表匠却说："她慢的地方，正是我们不出事的地方。"
>
> Agent 的工具层就是这位管钥匙的人。模型可以提出行动，但工具层决定这次行动能不能成为现实。

---

> **TL;DR**
>
> 工具层不是一组函数，而是一套受控行动系统。它用名称、描述和 Schema 告诉模型工具是什么，用注册表决定当前能看见哪些工具，用权限和参数验证挡住危险请求，用统一结果把成功与失败都反馈成可理解的观察。它让模型能动手，也让模型不能乱动手。

---

## 1. 工具不是普通函数

普通函数只关心输入和输出。Agent 工具还要面对一个更麻烦的调用者：模型。

模型会选错工具、漏传参数、编造不存在的路径，也可能要求执行一个当前用户没有权限的操作。工具层因此要把每个能力包装成稳定契约：

- 名称要唯一，避免模型在相似工具之间猜。
- 描述要说明适用场景、限制和相近工具差异。
- 输入 Schema 要表达字段、类型、必填项和范围。
- 调用接口要支持超时、取消、进度和并发。
- 结果要统一表达成功、失败、错误类型和可反馈内容。

Schema 只能证明结构正确，不能证明操作安全。路径在 Schema 里是字符串，但它可能逃出工作区；命令在 Schema 里也是字符串，但它可能删除文件。工具层必须继续做语义验证和安全验证。

## 2. 一次工具调用要走完整流水线

模型说"调用工具"，系统不能立刻照办。一条可靠流水线通常包含六步：

1. 发现工具：按名称找到真实可执行的工具。
2. 检查权限：确认当前用户、项目、会话策略允许调用。
3. 验证输入：先做 Schema 检查，再做路径、命令、资源边界检查。
4. 执行工具：在超时、取消和资源限制下接触外部世界。
5. 处理结果：脱敏、截断、序列化，并保留错误类型。
6. 记录审计：写下谁在何时做了什么，耗时多少，结果怎样。

任一步失败，都应该提前返回统一错误结果。这个错误不只是报错文本，它是下一轮推理的观察。文件不存在、权限不足、执行超时代表不同的环境反馈，模型看到具体原因后，才有机会换路径、改参数或向用户确认。

## 3. 权限要靠近副作用

工具层处在"语言意图"变成"真实副作用"的位置，所以它必须默认谨慎。

只读工具可以低门槛开放。写文件、改数据库、发邮件、执行 shell 这类工具要走更严格的策略。高风险工具应默认拒绝，只有在上下文、权限和审批都明确时才放行。

安全规则也要放在最接近副作用的地方。文件工具自己做路径边界检查，shell 工具自己做命令解析和危险操作拦截，网络工具自己做域名、凭据和速率限制。统一权限网关能处理角色和会话策略，但具体工具最了解自己的危险边界，两层都不能省。

并发同样要受治理。两个读取操作可以并发，写同一个文件的两个操作不能只因为"异步"就同时执行。工具是否能并发，取决于依赖关系、副作用、资源竞争和外部服务限额。

## 4. 工具越多，越要少暴露

把所有工具一次性交给模型，看起来能力最强，实际会带来选择噪声和上下文成本。工具多了之后，注册表要承担能力目录的职责：按会话、项目、权限和任务动态决定当前暴露哪些工具。

缓存也要分清层次。Schema 缓存减少重复构建和远程发现开销；结果缓存减少重复调用；状态缓存帮助工具理解外部世界是否变化。缓存的难点是失效：工具版本、权限、文件状态、远程服务能力一变，旧缓存就可能误导模型。

扩展工具系统时，有三种常见手法：

- 装饰器给已有工具加超时、重试、日志、指标。
- 复合工具把稳定多步流程包装成一个高层能力。
- 条件工具在同一个接口下按环境选择本地或远程实现。

这些手法都服务同一件事：减少模型需要做的选择，把真正需要治理的地方留给工具层。

## 写在最后

后来，那位学徒也成了师傅。他终于可以随意进出工具室，却仍然把每次取用都写进账本。

新学徒问他："您已经是师傅了，为什么还要登记？"

他说："因为我不是怕自己拿不到工具，我是怕自己拿到太多工具。"

管钥匙的人没有修过一座钟。镇上的人也不会在庆典里提起她。但每一座按时响起的钟，都经过她的桌前。她不让天才失去行动力，她只让每一次行动都有边界、证据和归路。

工具层也是这样。它不替模型思考，但它决定模型的想法怎样安全地碰到真实世界。
