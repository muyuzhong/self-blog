# 任务编排与工作流引擎：给工坊排班的人

> **引言**
>
> 镇上要建一座新的报时塔。钟表匠说他能做齿轮，木匠说他能搭梁，石匠说他能砌墙。每个人都很能干，但如果他们一起冲进工地，木梁会压在未干的石灰上，钟盘会比塔身先运到屋顶。
>
> 工地上来了一位排班人。她把整件事画成一张图：先打地基，再立塔身，木梁和钟盘可以并行准备，齿轮必须等主轴尺寸确定后再加工。需要动火的地方先停下等批准，某个工序失败就回到最近的检查点。
>
> 她不比钟表匠更懂齿轮，也不比石匠更懂石头。她懂的是顺序、依赖、责任和恢复。
>
> 复杂 Agent 系统里的编排层，就是这位排班人。

---

> **TL;DR**
>
> 运行时管理一条 Agent 循环内的下一步，编排层管理跨循环、跨任务、跨智能体的整体调度。它用 DAG 表达依赖与并行，用状态机表达分支、审批和重试，用角色拆分解决上下文退化和自评偏差，用可靠通信把各个执行单元连起来。

---

## 1. 大任务要先画成 DAG

单条 Agent 循环适合处理连续任务。现实里的复杂任务往往不可原子，也不该串行。例如"评估一篇论文"至少包含获取文本、提取元数据、分析内容、核对引用、检查格式、汇总报告。内容分析和引用分析没有依赖，可以并行；汇总报告必须等前面都完成。

DAG 用节点表示任务，用箭头表示依赖。它带来三件工程收益：

- 无环，避免任务互相等待。
- 可拓扑排序，调度器能找到合法执行顺序。
- 可并行，互不依赖的节点能同批执行。

任务粒度要适中。太粗会浪费并行机会，太细会让调度成本超过任务本身。一个实用范围是让单个任务预期持续十秒到十分钟。低于一秒的节点倾向合并，超过十分钟的节点倾向继续拆分。

还要区分数据依赖和控制依赖。数据依赖需要传结果，控制依赖只需要确认前序完成。两者都画成箭头，但通信成本完全不同。

## 2. 工作流引擎把提交边界画进流程

DAG 擅长表达谁先谁后，不擅长表达分支、重试、审批和暂停。工作流引擎用有限状态机处理这些问题。

状态机包含状态、事件、转移函数、初始状态和终止状态。它能清楚表达：验证失败走拒绝，执行超时走重试，高风险副作用先进入等待审批，人工批准后才提交。

这里最重要的设计，是给动作标出是否有副作用。读取、分类、验证可以直接执行；写文件、改数据库、调用危险 API 要先停在安全点。这个"副作用暂停"把运行时里的候选与已提交边界放进了流程图。

工作流也要有检查点。保存当前状态、上下文和已执行动作，进程崩溃后才能从最近的已验证状态恢复，而不是重新跑一遍可能带副作用的步骤。

## 3. 多智能体编排要拆职责

复杂任务里，单个智能体会遇到两个问题：上下文越来越浑，自评越来越松。

编排层可以把职责拆给不同角色。Planner 负责把模糊目标拆成计划和验收标准；Generator 负责按计划生成结果；Evaluator 负责用独立视角检查结果。评估者不只是锦上添花，它能从结构上绕开模型给自己打高分的问题。

多个智能体协作时，要控制上下文传递。子智能体可以用自己的窗口探索大量细节，最后只把精炼摘要和关键证据交回主流程。并发子智能体也要隔离本地变量，只有显式提交的结果才能进入父上下文，避免互相污染。

多智能体不是越多越好。它更慢、更贵，适合那些质量、覆盖面和独立评审比速度重要的任务。

## 4. 通信要守住可靠性、顺序和背压

智能体之间的通信有两种基本范式：消息传递和共享内存。默认应优先消息传递，因为它松耦合、易扩展、适合分布式；只有低延迟且关系紧密的场景，才考虑共享内存。

可靠通信有三条底线。

第一，至少一次送达要配合幂等性。系统会重试，重试就可能重复，所以接收方必须用幂等键避免重复副作用。

第二，需要有序的消息要按 key 进入顺序队列。同一个任务的状态更新不能乱序处理。

第三，队列要有背压。消费者追不上时，发送方必须减速或暂停，不能让消息无限堆积直到耗尽内存。

这些机制听起来像消息系统常识，但在 Agent 编排里更关键。因为一次乱序、重复或丢失的中间结果，可能让后续模型基于错误状态继续推理。

## 写在最后

报时塔建成那天，镇上的人赞美钟表匠的齿轮、石匠的墙、木匠的梁。排班人站在图纸旁边，把最后一个完成标记划掉。

学徒问她："这座塔里哪一块是您做的？"

她说："没有哪一块是我做的。可如果没有顺序，每一块都会挡住另一块。"

编排层也不直接生成最终答案。它把复杂任务拆开，把依赖排清，把副作用停在该停的地方，把不同角色的工作接起来。一个好的编排引擎不炫耀自己，它只让复杂工程按可重放、可恢复、可审计的方式前进。
